# سیاست مستندسازی و بومی‌سازی CakeBazar

**وضعیت:** پذیرفته‌شده برای Founder Reset v1  
**مالک:** بنیان‌گذار  
**آخرین بازبینی:** ۲۰۲۶-۰۷-۱۰  
**دوره بازبینی:** ماهانه در مرحله اعتبارسنجی  
**نسخه انگلیسی:** [DOCUMENTATION_POLICY.md](DOCUMENTATION_POLICY.md)

## هدف

مستندات، سیستم تصمیم‌گیری و حافظه بلندمدت CakeBazar هستند. آن‌ها باید به بنیان‌گذار، اعضای آینده تیم، اپراتورها، سرمایه‌گذاران و عامل‌های هوش مصنوعی کمک کنند بفهمند چه چیزی اکنون واقعیت دارد، چه چیزی فقط فرضیه است و چه چیزی آگاهانه به آینده موکول شده است.

## ۱. استاندارد دوزبانه

هر سند جدید یا هر سند قابل‌خواندن برای انسان که به‌طور اساسی بازنویسی می‌شود، باید به‌صورت یک جفت فایل ارائه شود:

- انگلیسی: `DOCUMENT_NAME.md`
- فارسی: `DOCUMENT_NAME.fa.md`

دو فایل باید یک وضعیت تصمیم را منعکس کنند. ترجمه طبیعی و روان بر ترجمه کلمه‌به‌کلمه ترجیح دارد.

این قانون شامل استراتژی، نیازمندی‌های محصول، تحقیق، عملیات، توضیحات معماری، اسناد مالی و سرمایه‌گذاری، راهنمای مشارکت‌کنندگان، دستورالعمل عامل‌ها و سیاست‌های قابل‌مشاهده برای کاربر است.

کد منبع، lockfile، فایل‌های تولیدشده، تنظیمات ماشینی، migrationها، تصاویر و فایل‌های باینری مستقل از زبان هستند و کپی نمی‌شوند. متن قابل‌مشاهده برای کاربر باید آماده بومی‌سازی باقی بماند.

## ۲. منبع حقیقت مرجع

هر موضوع فقط باید یک سند مرجع داشته باشد. اسناد دیگر می‌توانند به آن لینک دهند، اما نباید بدون اعلام، تعریف دیگری ایجاد کنند.

| موضوع | محل مرجع |
|---|---|
| جهت فعلی شرکت | `docs/strategy/FOUNDER_RESET.md` |
| کار اعتبارسنجی فعلی | `docs/execution/PHASE_0_PLAN.md` |
| فهرست اجرای Codex | `docs/execution/CODEX_TASKS.md` |
| مدل همکاری هوش مصنوعی | `AI_COLLABORATION.md` |
| زمینه فعلی پروژه | `PROJECT_CONTEXT.md` |
| تصمیمات مهم | `docs/decisions/DECISION_LOG.md` |
| شواهد و یادگیری‌ها | `docs/research/` |
| ایده‌های آینده | `docs/ideas/` |
| وضعیت فعلی پیاده‌سازی | `README.md` ریشه مخزن |

اگر اسناد با هم تعارض داشتند، جدیدترین سند مرجع پذیرفته‌شده ملاک است و تعارض باید برای پاک‌سازی ثبت شود.

## ۳. سربرگ الزامی سند

هر سند مرجع بهتر است موارد زیر را مشخص کند:

- وضعیت: پیش‌نویس، پیشنهادشده، پذیرفته‌شده، جایگزین‌شده یا بایگانی‌شده
- مالک
- تاریخ آخرین بازبینی
- محرک یا دوره بازبینی بعدی
- لینک نسخه زبان دیگر

## ۴. برچسب‌های شواهد

ادعاهای مهم باید با یکی از برچسب‌های زیر مشخص شوند:

- **مشاهده‌شده:** مستقیماً اندازه‌گیری یا مشاهده شده است
- **اعتبارسنجی‌شده:** با شواهد تکرارشونده و در برابر آستانه از پیش تعیین‌شده پشتیبانی می‌شود
- **فرضیه:** منطقی است، اما هنوز آزمون نشده است
- **فرض برنامه‌ریزی:** برای برنامه‌ریزی استفاده شده و عدم قطعیت بالایی دارد
- **برآورد:** تقریب عددی همراه با روش و تاریخ
- **تصمیم:** انتخاب صریح همراه با منطق

تکرار یک فرضیه در چند سند، آن را به واقعیت تبدیل نمی‌کند.

## ۵. وضعیت فعلی در برابر وضعیت هدف

اسناد محصول، معماری، رقبا، مالی و سرمایه‌گذاری باید این موارد را جدا کنند:

- `اکنون پیاده‌سازی شده`
- `در پایلوت به‌صورت دستی انجام می‌شود`
- `گام بعدی برنامه‌ریزی‌شده`
- `گزینه آینده`
- `رد یا متوقف شده`

قابلیت‌های آینده نباید به‌عنوان مزیت رقابتی فعلی شمرده شوند.

## ۶. انضباط مالی

هر عدد مالی باید شامل موارد زیر باشد:

- ارز و واحد
- تاریخ یا مبنای قیمت
- منبع یا روش محاسبه
- سطح اطمینان
- مالک
- تاریخ بازبینی

اعداد اعتبارسنجی‌نشده باید به‌عنوان فرض مشخص شوند. درآمد با حاشیه مشارکت برابر نیست. ارزش طول عمر مشتری معمولاً باید بر اساس حاشیه مشارکت محاسبه شود، نه درآمد ناخالص.

## ۷. انضباط تحقیق

قالب مصاحبه، شواهد محسوب نمی‌شود. هر رکورد تحقیق تکمیل‌شده باید شامل موارد زیر باشد:

- شناسه شواهد
- بخش کاربری شرکت‌کننده
- تاریخ و بازار
- منبع جذب
- ارجاع به یادداشت یا متن جلسه
- مشاهدات مستقیم
- تفسیر
- سطح اطمینان
- اثر بر تصمیم

اطلاعات شخصی حساس باید تا حد ممکن کم جمع‌آوری و محافظت شوند.

## ۸. انضباط تصمیم‌گیری

هر تصمیم مهم باید شامل موارد زیر باشد:

- تاریخ دقیق و مالک
- مسئله یا محرک
- گزینه‌های بررسی‌شده
- شواهد موجود
- گزینه انتخاب‌شده و منطق آن
- ریسک‌ها
- قابل‌بازگشت یا غیرقابل‌بازگشت بودن
- محرک بازبینی
- وضعیت

## ۹. قواعد هوش مصنوعی و Codex

محتوای تولیدشده توسط هوش مصنوعی تا زمان بررسی در برابر شواهد، پیش‌نویس است.

Codex باید قواعد مخزن را از طریق `AGENTS.md` و معیارهای پذیرش مخصوص هر وظیفه دریافت کند. هر وظیفه پیاده‌سازی باید:

1. به یک Issue یا شناسه وظیفه لینک داشته باشد.
2. محدوده داخل و خارج کار را مشخص کند.
3. هنگام تغییر رفتار، تست اضافه یا به‌روزرسانی کند.
4. بررسی‌های لازم را اجرا کند.
5. هر دو نسخه زبانی مستندات قابل‌خواندن تغییرکرده را به‌روزرسانی کند.
6. یک Pull Request متمرکز باز کند.
7. از ساختن شواهد بازار، نتیجه حقوقی، اثبات مالی یا نیازمندی محصول بدون منبع خودداری کند.

## ۱۰. مهاجرت اسناد قدیمی

اسناد فعلی که دوزبانه در یک فایل، تکراری، خالی یا بیش از حد آرمانی هستند، بدون بررسی حذف نمی‌شوند. آن‌ها در یکی از گروه‌های زیر قرار می‌گیرند:

- مرجع و دارای جفت زبانی
- ادغام‌شده در سند دیگر
- تاریخی یا legacy
- بایگانی‌شده
- حذف‌شده به‌عنوان فایل تصادفی

تا پایان این مهاجرت، README ریشه و اسناد پذیرفته‌شده Founder Reset حقیقت فعلی پروژه را تعریف می‌کنند.
